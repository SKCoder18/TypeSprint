# Current production setup

The Vercel website uses browser-local profiles without email confirmation. `/api/race` accepts a random per-profile player capability, never the local email or password. Completed local-profile races, including private rooms and Quick Match, save community leaderboard totals atomically with room state. These scores are not verified identities and never write the legacy verified-account leaderboard. Highest WPM is retained across lower later results; duplicate polls cannot award a match twice. All-time totals and the most recent eight active weekly buckets per player survive room cleanup.

Apply `supabase/live-race-setup.sql` once. Keep `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` and the exact production `SITE_URL` in Vercel's server environment. Live rooms use server-only Supabase storage with revision-checked atomic updates and replay the existing race simulation on each request. The separate `race:server` process is no longer required by the website. Public and authenticated Supabase keys have no access to room storage.

This initial deployment supports 20 retained rooms. Waiting rooms expire after five minutes, inactive connections after 30 seconds, and finished rooms are removed on subsequent requests after two minutes. Global optimistic concurrency favors a small deployment; load testing and partitioning room storage are needed before expanding capacity. Server timestamps and sequence checks govern movement; local profiles are not verified identities.

# Legacy verified-account server setup

No resources were created and nothing was publicly deployed. The application uses Supabase's Auth and PostgREST HTTP APIs through server routes; no browser service-role key or extra SDK is required.

1. Create or choose your Supabase project yourself. Apply `supabase/migrations/001_phase3.sql` once in its SQL editor. Back up an existing database first. The schema is additive, but table names must not already exist. Enable email confirmation, SMTP, auth rate limits and password policies in Supabase.
2. Put SUPABASE_URL, SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY in `.env.local` (never the example or frontend). Configure SITE_URL to the exact HTTPS origin in production. Set the same origin and `/account` redirect URL in Supabase Auth. Recovery/confirmation links exchange tokens into HttpOnly SameSite cookies; password reset uses the Account password screen. Restrict server logs and do not log requests containing credentials.
3. Run `npm run race:server` in a separate terminal and `npm run dev` for the website. For production run `npm run build` and `npm start`, plus the separate long-running race process. Keep RACE_SERVER_URL private. The service binds loopback; use a private network or colocate the processes. An ordinary short-lived serverless handler cannot own authoritative race state.
4. The race service is single-process, memory-resident. Route every participant to that one service. A restart cancels live rooms; completed ranked results persist transactionally through record_race. Add durable session storage, coordinated matchmaking and operational monitoring before scaling. Do not run multiple independent replicas behind round-robin routing. Disconnections stop movement after three seconds and allow a 30-second reconnect. Explicit leave, timeout and anomalies cancel without ranking.
5. Configure CONTACT_EMAIL before launch and review Privacy/Terms with actual operator identity, retention and deletion procedures. No analytics/ads/nonessential cookies are currently loaded, so no nonessential cookie consent is requested. If adding them later, implement consent before loading tags in applicable regions. No AdSense script, fake ad or approval claim is included. Reserve future placements in static informational content only, away from all active gameplay and controls.
6. Set DNS/domain/TLS on your chosen host. Confirm auth redirects, secure cookie behavior, CORS/private networking, email delivery, rate-limit proxy headers and database policies using two independent signed-in clients. Production requires HTTPS; local development uses the dev server.
7. Search Console: verify domain ownership, check canonical SITE_URL, submit `/sitemap.xml`, inspect important routes and confirm robots allows the production domain. Preview/local robots disallows indexing.
8. AdSense: publish accurate About/Contact/Privacy/Terms, verify ownership and regional consent requirements, review content and trademark rights for summaries, confirm keyboard/mobile usability and submit through your approved publisher account. Approval is not guaranteed.

## Trust and verification boundaries

Offline results and imported achievements are explicitly unverified. Cloud merge is opt-in and keeps local data. Only the race service can invoke record_race; duplicate match IDs fail atomically. Browser RLS policies deny match/winner/leaderboard writes. Verified rankings are based on a fixed server passage, ordered input packets, server receipt time and a 20-key/second budget with burst limits. Scripted typing, collusion, account farming and sophisticated bots are still possible; this is not full cheat resistance. Private rooms are unranked; Quick Match requires authentication.

Cloud sync runs while a signed-in page is open and only after explicit Import/Merge. It retries on later intervals and leaves local data intact on failure. Concurrent updates from multiple devices use a best-effort merge, not a transactional CRDT; make sequential imports if coordinating devices. Guest gameplay requires no backend.

## Required prelaunch verification (not completed without credentials)

Apply migration to a test project and exercise RLS with two users, signup confirmation, recovery, cookie refresh, imported progress and verified rankings. Run two devices over HTTPS through a private room and Quick Match, test reconnect and server restart, and inspect service logs for persistence failures. Review query plans and load-test the polling transport. Do not call this production-ready until those checks and operator configuration are complete.
